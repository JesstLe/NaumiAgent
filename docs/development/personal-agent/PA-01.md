# PA-01：个人事项、单次执行和结果收件箱

日期：2026-11-04

状态：**partial / 本机单次事项纵向模块已完成真实验收**。
本模块不是整个 Personal Agent 产品已完成；24 项视频要求、PA-00～PA-11 的原范围保持不变。

## 1. 产品模型

用户可以同时维护工作、生活、学习等多个事项。每个事项明确绑定主 Agent 或用户已经创建的
一个独立 Agent，不预置职业、不在执行时创建常驻身份，也不更改用户给 Agent 取的名称。
事项可以立即执行或按明确 IANA 时区的一次性时间执行。

实际链路为：

```text
人工 UI / /items / personal_items Tool
  → 同一 PersonalItemService
  → 不可变委托修订与原请求回执
  → Scheduler 的 personal_item 到期事件
  → prepared 原始请求和确切输入清单
  → 既有共享 AgentJob 容量 / FIFO / claim
  → 独立执行 Session 与真实 Engine Run
  → 私有 Library 报告
  → 同 JobStore 的 publication 和 execution-session inbox
  → 人工明确确认的 human_result_read 回执
```

事项不占用或放宽已有“每工作区一个未结束 Goal”的约束，也不新造一套 running/completed/read
布尔字段。Job、Run、产物、投递、人工已读分别保留自己的权威记录。

## 2. 状态、幂等与恢复

- Item header 只有 `active/paused/cancelled/closed`，以 `revision` 做 CAS；每次明确再次执行产生新的
  `once_key`，普通暂停/恢复不改变它。
- 创建、修改、控制和再次执行均保留原 request_id、原完整请求摘要。`mode=now` 的重试不会重新采样
  一个时间，也不会把原控制请求应用到 restart 后的新一次委托。
- `run-now` 先保存控制回执，再触发原 schedule 的同一个 event；不会创建第二个 occurrence。
- 到期事件只有在 prepared 身份或机械决定持久化后才消费。`input-error` 是模型开始前的真实输入错误，
  不是 Job 终态，也不是“未知执行已失败”。恢复不会改写已有决定的意义。
- 暂停仅适用于尚未 Job admission 的事项或 prepared 请求。已进入共享 FIFO 的 Job 使用取消结束，
  避免一个“暂停的队首”挡住所有其他 Agent。跨进程竞态在开始前再次核验，未启动的真实 Job
  通过原 JobStore 机械取消，不隐式重新收费。
- 持久 RUNNING 丢失执行者、租约过期、模型或 Run 用量证据缺失时保留 UNKNOWN；不会当成未受理重发。
- 已绑定 Job 原件消失时拒绝重新 admission。已完成结果缺失原 Run 或 receipt 摘要不一致时，
  不继续声称完成。
- Store 实例 ID 和 Session DB 旁的独立 witness 防止整个事项目录丢失后悄悄换成空库。
- Scheduler 以 SQLite 原子提交事件、计数和终态；扫描用 `(fired_at,id)` 游标，暂停事件不阻断后续事项。

## 3. 输入与执行边界

- 输入是当前执行 Agent 已获授权的确切 PA-08 artifact/version/SHA/grant/revision，或用户明确选取的
  当前工作区资料目录。不隐式分享，也不以新 grant 替换已经撤销的旧 grant。
- 最多 8 个目录、合计 64 份输入、每文件 20 MiB、总体 50 MiB。目录在 dispatch 时实际读取字节，
  保存 SHA 和来源清单；数量、大小、链接/硬链接/reparse、目录变化、读取前后文件身份都实际校验。
  不静默截断文件。给模型的文本摘要有独立、明确的字符截取标记。
- Item 工具范围与实际 Agent 配置、系统权限相交；资料操作只允许 `get/read/publish`，对象级限制只含
  本次输入和自己的输出。模型没有人工已读操作，也不继承认证 GUI 的跨 Agent 管理身份。
- 主 Agent 和个人 Agent 均冻结模型 tier、工具范围、直接运行路径和逐边界租约；不套第二个委派 Job。
- 即使输入为空，计算也强制进入真实 Docker；本次 `/workspace` 是全新空目录，而不是宿主快照。
  `/inputs` 只有确切版本；`/outputs` 由 broker 发布。原 PA-08 计算模式的 32 文件 / 20 MiB 限额不变，
  Item 的空工作区模式真实支持 64 文件 / 50 MiB。
- 隔离进程返回后和每次输出发布前再次核验 Item / claim，取消或失效的旧执行不会继续交付文件。
- 模型没有生成合适的 Markdown/Page 报告时，基础设施将本轮真实最终回答保存成不可变 Markdown，
  绑定原 Job、Run、receipt 和来源，不伪造报告。
- 输入授权撤销后，结果视图不返回回答、Run steps、receipt 正文或衍生内容；历史消息与 Run HTTP
  入口也核验原输入引用，避免从另一入口绕过。

## 4. 用户入口

- Web2 浅色“事项”工作区：进行中 / 已暂停 / 全部，创建/编辑、控制、修订历史、历次执行、Run 与报告。
- 结果收件箱：未读 / 全部。查看、刷新、GET、Agent 消费不算人工已读。只有明确按钮或手动命令
  才生成引用 exact delivery/hash 和 legacy ACK 的 typed human receipt。
- CLI / TUI / Web 斜杠命令共享 `/items` parser 和真实 `Engine.execute_tool()`；可信人工 read
  单独进入同一 service。模型不能传 actor、owner、route、trusted_channel。
- UI 持久保存未知写入的原 request_id 与完整 payload，恢复后保留原身份；不因 503、超时或列表缺行
  生成一个新的请求。未保存编辑具有导航与关闭保护。

接口细节见 [接入层记录](../pa01-personal-items-interfaces.md) 与
[界面记录](../pa01-personal-items-ui.md)。冻结合同、源码原件及执行证据保存在
`.naumi/transactions/pa01-20261104/`，最终字面命令、退出状态与回滚证据以 `VERIFICATION.txt` 为准。

## 5. 当前验证与剩余验收

已观察到 Store 47 项、接入层及既有入口 181 项、执行器及其相关回归 114 项通过；
Service/Scheduler 24 项、真实 Engine HTTP 4 项、隔离边界与原 Docker 模块 76 项通过；
前端完整 29 files / 282 tests 通过，生产构建通过。上述为各批次实际记录，不相加冒充去重总数。

最终相关后端回归为 2311 passed / 7 failed / 3 skipped；七项均已在原始源码中逐项复现，不能称全仓库通过。
三个真实 provider 事项已分别得到销售合计 159.50、支出合计 96.00、正确率 80%；输入 SHA、
三次真实 Docker、三个 exact Run / 报告 / delivery 均已核对，并观察到真实 Run 重叠。
浏览器管理 10 项与收件箱 7 项通过；只显式已读 Echo 一条，另两条保持未读。
冷重启后全部原事项、Run、消息、投递与 human receipt 完全一致，零新增 Run。
源码副本回滚仍由最终事务记录独立收口。测试替身、真实 Docker、真实 provider、浏览器、安装/发布属于不同证据层。
尚未记录的层级不从前一层推导通过。

周期规则与主动建议仍属于 PA-04；语义记忆属于 PA-02；账户与外部行动属于 PA-03/PA-09；
设备通知、语音、原生电脑和多设备分别按原模块继续实现。这些不是以当前单次事项替代的能力。

JobStore schema v8 为人工已读新增 append-only 表，保留原 legacy ACK 摘要。
源码副本回滚不降级已经迁移的真实用户数据库，不恢复模型用量或外部行动；测试数据库均与用户数据隔离。

## 6. 可复用委托示例

下面是给主 Agent 的任务描述；保存事项前仍需实际选择 Agent、材料与时间，不由文字扩大授权：

```text
把我选中的资料安排在指定时区的明天 9 点处理，交给我已经创建的 Echo。
实际读取确切版本；需要计算时在隔离环境执行，保存带来源的报告到 Echo 的资料库。
在结果收件箱保留 Job、Run 和投递凭据。状态未知时核对原执行，不新建一次执行。
不要自动创建或重命名 Agent；不要把查看结果当成人工已读。
```
