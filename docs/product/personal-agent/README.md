# NaumiAgent Personal Agent 产品方向

日期：2026-11-03

状态：产品范围已确认；架构、模块划分和实施顺序为提案；运行功能尚未在本轮实现。

## 1. 已确认的产品范围

用户希望 NaumiAgent 成为 Personal Agent，并明确同时覆盖：

1. **个人执行助理**：持续跟进个人事项、按约定触发行动、交付结果。
2. **个人工作助理**：代码、文档、调研、资料整理和项目推进。
3. **个人生活助理**：日程、邮件、资讯、学习和日常安排。

这不是三个独立助手，也不是把编程 Agent 的名称改成个人助理。
三个领域共享个人档案、事项、执行记录和结果收件箱；工作区变为上下文之一，
不再是产品顶层身份。工作与生活的具体数据仍保持明确的作用范围。

**产品定义：一个认识用户、掌握相关上下文、能够接受委托并持续完成工作与生活事务的个人 Agent。**

目前尚未由用户选定：第一个邮箱/日历平台、移动端优先级、云端常驻方案以及公开商业化受众。
以下默认建议以单用户桌面为第一验证入口，同时为个人多设备留出身份和同步边界；
这不是对最终平台覆盖的收缩。

## 2. 用户价值与边界

### 理解我

- 能记住明确偏好、长期目标、常用资料位置和已确认的工作方式。
- 分清用户原话、外部材料、助手建议和待确认推断，不能把自己的建议记成用户要求。
- 每条重要记忆有来源、范围、更新时间和状态；用户可以查看、纠正、删除、导出。
- 工作区资料不自动变成全局个人记忆；“个人 / 项目 / 单次任务”必须明确隔离。

### 替我做事

- 用户交代事项后，得到真实事项 ID、执行状态、需要确认的动作和结果位置。
- 工作：读取指定文件、调研、写文档、生成代码和验证产物。
- 生活：处理日程与待办、准备邮件草稿、整理学习材料及信息；逐个接入真实服务。
- 持续执行：依据时间或已连接事件触发、跨会话继续、失败后恢复或请求用户决策。
- 整理材料等已授权动作可自动执行；发送、购买、删除、发布等外部变更采用具体授权规则，
  绑定账户、对象、动作、有效期和额度，并提供清楚的待确认入口与撤销授权能力。

### 主动但不打扰

- 主动来源是用户委托、已确认规则或已连接事件，不是无依据地自行扩展目标。
- 汇总低优先级消息，尊重勿扰时间，只在需要决策、完成交付或重要失败时通知。
- 桌面前台关闭不应丢失事项；后台服务退出、设备休眠或关机后的执行语义要明确。
- 本机关闭时不承诺仍能执行。持续在线能力需要实际常驻设备或后续云端执行器。

## 3. 当前源码事实

以下仅为本轮只读源码核对，不代表这些能力已通过新的运行态验收。

### 可以复用的基础

- `src/naumi_agent/memory/long_term.py`：持久向量记忆、分类、去重、衰减和遗忘。
- `src/naumi_agent/orchestrator/goal_store.py`：SQLite 目标状态和事务转换。
- `src/naumi_agent/daemons/agent_jobs.py`：持久执行、租约、fencing、终态、结果 inbox 与交付回执。
- `src/naumi_agent/runs/`：Run 记录、恢复、公开活动和工具证据。
- `src/naumi_agent/scheduler/`：once/cron、持久事件、暂停/恢复/取消。
- `src/naumi_agent/tools/` 与 `mcp/client.py`：文件、浏览器、工具和 MCP 桥接。
- `frontend/web2/`、桌面壳与 CLI/TUI：现有交互入口；不再另造一套执行引擎。

### 四个关键缺口

1. **个人档案**：现有 `global` 召回范围不等于跨工作区的个人身份层。
   `memory/auto_extract.py` 拼接用户和助手文本再提取；相似记忆合并偏向保留更长文本，
   尚不足以处理来源权威、旧偏好撤销与新偏好覆盖。
2. **个人事项**：`GoalStore` 保持每工作区一个未结束目标；现有 session Task 偏执行协作。
   个人同时推进多项工作和生活事务，不宜直接放宽执行层不变量来充当事项系统。
3. **主动执行与送达**：`ScheduleTarget` 只有 `session_message`；
   `collect_notifications()` 取出事件即标记 delivered，engine 在交互循环中注入通知。
   “到了时间 / 派发成功 / 用户设备已展示 / 用户已读”尚未构成完整个人送达链。
4. **个人账户连接**：通用 stdio MCP 工具发现不是邮箱和日历产品接入。
   定向检索尚未发现完整的个人账户连接、授权续期、同步游标、增量事件与断连提示链。

## 4. 建议的共享架构

```text
个人入口：桌面 / Web / CLI-TUI / 后续移动入口
                    ↓
个人上下文：用户档案、分范围记忆、工作区与已连接服务
                    ↓
个人事项：目标、截止时间、优先级、重复规则、授权策略
                    ↓
触发与编排：时间 / 服务事件 / 用户继续 / 有界主动建议
                    ↓
已有执行底座：Goal / AgentJob / Run / Tools / MCP
                    ↓
结果与送达：产物、依据、执行回执、通知状态、用户确认
```

### 数据职责

- **Person / Profile**：个人身份与显式偏好；凭据引用不混入向量记忆。
- **Memory**：带来源、范围、状态和修订记录的事实与偏好。
- **PersonalItem**：长期委托，包含工作/生活领域、截止时间、优先级、状态及策略。
- **Trigger**：时间与时区、事件订阅、去重键、错过触发策略。
- **Run**：一次实际执行；复用已有运行态 ID、取消、恢复和证据，不创建第二套执行状态机。
- **Artifact / Delivery**：结果文件与送达记录；生成成功、送达成功和已读分别记录。
- **Connection**：账户、能力、授权引用、同步游标和健康状态。

一个事项可以产生多次 Run；任务已触发不等于已完成，报告已生成不等于用户已经收到。
执行结果不明时保留 UNKNOWN，不为填满完成列表而自动重复外部变更。

## 5. 建议的产品界面

继续采用浅色布局和已确认的黑白 N 品牌，避免解释性标语。

一级入口建议保持五项：

1. **今日**：需要用户处理的确认、今天的事项、已完成交付。
2. **对话**：交代任务、补充上下文和讨论结果。
3. **事项**：工作/生活/学习分类，进行中、等待、到期与周期事项。
4. **记忆**：用户资料、偏好、事实与来源；提供纠正和删除。
5. **连接**：文件位置、邮箱、日历及其他真实账户的状态。

工具、模型、日志、评测和自进化进入设置或开发者视图，不把内部能力名称当作普通用户主导航。
首模块先接入现有界面的真实事项入口，数据链通过后再逐步迁移导航，避免静态空壳首页。

## 6. 分模块实施提案

以下 PA 编号仅用于本产品提案，尚未并入 `docs/development/module-registry.yaml`。
立项实现前需完成对现有 33 个工程模块的依赖映射，避免重复 owner 和状态记录。

### PA-01：个人事项到结果的完整闭环

**状态：planned。建议第一个实现。**

示例委托：“明天 9 点整理我指定目录里的资料，给我一份带来源的摘要。”
可以是项目周报，也可以是旅行、学习或生活资料；用同一闭环覆盖三个领域，
不把首模块做成只服务编码的功能。

交付：
- 创建、查看、修改、暂停、取消与确认事项；显式时区和输出位置。
- 先支持一次性时间触发，在无聊天消息输入时调度已有 AgentJob/Run。
- 复用文件工具执行，输出真实报告与来源；提供结果收件箱与站内送达状态。
- 以已有桌面渠道能力为准接入通知，通知失败不丢结果、不伪装成已读。
- Web 与 Agent Tool 共享 service，CLI/TUI 提供同一能力入口。

验收：
- 读取用户指定的真实文件，产生可打开且可追溯的真实产物。
- 关闭对话页但服务在线仍执行；服务重启后继续，不重建已完成任务。
- 重复触发、并发派发、到点前后取消、超时、输出目录异常均有明确结果。
- 区分已执行、未知、待确认、已送达和已读；送达中断后恢复。
- 本机休眠后按明确规则补执行或跳过，不默认重放全部过期任务。
- 保留现有“每工作区一个执行 Goal”的约束，通过 Run 绑定或串行队列协调，而非直接移除约束。

### PA-02：可信个人记忆与跨工作区上下文

**状态：planned。依赖 PA-01 的个人身份及事项上下文。**

交付：个人/工作区/事项三层范围，来源区分、显式保存、偏好冲突处理、修订与删除，
用户可见的记忆面板，以及有范围的检索注入。

验收：在两个工作区复用已确认个人偏好，不泄露项目资料；助手建议不提升为用户事实；
纠正后旧条目撤权，删除后不再召回，重启后仍保持结果一致。

### PA-03：真实个人服务连接

**状态：planned。先选一个服务完成，再接下一个。**

建议从用户最常用的日历或邮箱开始，但当前未指定具体平台。
账户连接、最小读取范围、凭据保管、续期/失效、断连、增量同步与原始对象链接一起交付。
MCP 可以作为 adapter 的实现方式，不等于连接体验本身。

验收：至少一个真实账户完成读取→生成事项/草稿→用户确认→回写→读回对账；
相同事件重复到达只生成一次事项；授权撤销后停止使用该账户。

### PA-04：持续助理与主动跟进

**状态：planned。依赖前面的事项、记忆和真实事件。**

交付：周期委托、每日安排、跨工作区事项汇总、截止时间跟进、事件驱动的下一步建议、
通知合并/勿扰、成本与执行次数上限。

验收：多个工作与生活事项连续运行；用户只在需要决策时被打断；记录实际完成率、
需要人工纠正的次数、重复操作数、错误提醒数与交付耗时，而非只统计工具调用量。

### PA-05：多设备与可评估的个人化改进

**状态：planned。具体设备与常驻部署方案待产品选择。**

交付：移动端查看/确认、个人状态同步、设备角色和执行位置；
把经用户确认的重复流程沉淀为技能，复用已有评测与回滚机制决定是否采纳改进。

验收：手机确认与桌面任务状态一致，冲突可解释；设备离线不丢事项；
改进通过真实任务对照与回归后采纳，不让 Agent 直接改写当前生产状态。

## 7. 开发与完成标准

- 产品覆盖面完整，但按单模块交付，不同时搭建五个半成品。
- 新能力优先复用现有 service/store/runtime 接口，不复制第二套执行、调度或 inbox。
- 每模块完成真实用户路径后测试，覆盖错误、重启、幂等和并发边界；阶段门再做全量回归。
- 每模块维护实施记录、实际命令与结果、未完成项、回滚与独立英文 commit。
- 现有 Agent Control Center 全量测试超时仍是执行底座的已记录待查项；
  在依赖该链路的阶段验收前，需要重新定位和验证，不能由本产品文档消除。
- 本轮仅定义产品方向并核对源码，没有发布 Personal Agent 版本、接入账户或修改运行行为。
