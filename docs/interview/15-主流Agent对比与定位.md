# 15｜主流 Agent 对比：比较工程责任，不做功能宣传榜

[返回目录](README.md)

## 先分清比较的是什么

假设面试官问：“这些能力 LangGraph 也有，你为什么还做 NaumiAgent？”如果回答“我们有记忆、有工具、有多 Agent”，并没有建立差异，因为这些是常见能力。更好的回答先交代项目目标：它是一个用于理解和验证本地 Agent 执行、状态与治理的具体代码库；哪些地方选择自建、哪些借用依赖，以及为什么值得承担维护成本。

模型、SDK、编排 Runtime、Agent Harness 和最终产品处在不同层次。模型产生决策或文本；SDK 提供代码接口和运行原语；编排 Runtime 管执行与状态；Harness 为模型提供工具、上下文与运行约束；产品还包含用户入口、交付体验、运维和组织管理。一个项目可以跨越多层，但不能拿一个 SDK 的 API 数量与商业产品的全部功能比较。

这些系统的共同问题是：目标怎么表达，上下文从哪里来，如何选择动作，如何处理反馈、停止与人工介入。不同的是能力被谁提供、默认策略是什么、应用开发者还要补什么。以下是有依据的定位，不是经过统一跑分的优劣排名。

## 代表性形态与 NaumiAgent 的比较

| 对象 | 官方资料支持的定位 | 相同点与本项目取舍 |
| --- | --- | --- |
| LangChain / LangGraph / Deep Agents | LangChain 提供 Agent 抽象与集成；LangGraph 负责持久执行、流式与人工介入；Deep Agents 在其上提供规划、子 Agent、文件与上下文能力。 | 都涉及行动循环和状态。NaumiAgent 将这些工程问题放入自己的代码组织中；不能说它们“只有工作流、没有 Harness”。[官方概览](https://docs.langchain.com/oss/python/langgraph/overview) |
| OpenAI Agents SDK | 代码优先的 Agent 开发方式，包含运行、状态、编排、人类审查与观测入口，应用方仍承担部署、工具和相应存储/批准责任。 | 同样要处理工具和生命周期；NaumiAgent 的本地任务与治理契约是具体实现选择，不是 SDK 天然无法实现的功能。[官方 SDK 文档](https://developers.openai.com/api/docs/guides/agents/sdk) |
| Coding Agent，以 Claude Code 为具体例子 | 直接面向代码库阅读、文件修改与命令执行，并提供开发工具集成。 | 与 NaumiAgent 共享工作区动作和验证问题。比较时应选定具体终端或部署形态，不把整个产品系列当一个同质模块。[官方概览](https://code.claude.com/docs/en/overview) |
| Codex CLI | 在终端中读取仓库、修改文件、运行命令，也支持脚本化调用及执行权限选择。 | 同样涉及工作区和行动闭环；比较应落到具体权限与验证行为，不能把“能读写文件”当成 NaumiAgent 独有能力。[官方 CLI 文档](https://learn.chatgpt.com/docs/codex/cli) |
| Dify | Agent 可以作为工作流中的步骤；经典 Agent 节点支持模型动态决定工具调用，而非只能执行完全固定的顺序。 | 共同点是模型、工具与状态；区别是交付和配置入口，以及定制逻辑由平台还是应用代码承担。不能说“工作流一定不是 Agent”。[Agent 节点文档](https://docs.dify.ai/en/cloud/use-dify/nodes/agent) |
| 扣子 / 扣子编程 | 扣子编程同时涉及 AI 编程与低代码等开发方式，可构建智能体、工作流和应用。 | 与本项目都涉及任务、工具和扩展；NaumiAgent 提供可逐层阅读的自有 Runtime，平台产品承担更多搭建与交付入口。不能把扣子缩减成“只能拖拽”。[官方产品说明](https://docs.coze.cn/guides_welcome) |

这里分别核对了 Claude Code 与 Codex CLI 的官方说明，没有根据一次界面体验推断其全部内部实现，也不把一种产品的特定机制套到另一种。需要进一步比较时，应选定版本、运行环境与任务集，再讨论成功率、成本和安全边界。

## 当前资料特别需要修正的三个印象

第一，多模型接入不是某一项目独占优势。官方 Agents SDK 文档有模型与 Provider 配置专题；比较时应看任务实际用到的模型能力、工具协议和错误处理，而不是只数支持的模型名称。[模型与 Provider 文档](https://developers.openai.com/api/docs/guides/agents/models)

第二，图编排与动态决策不矛盾。图可以表达确定性节点，也能容纳根据模型输出选择下一步的节点；“用了图”并不意味着只能跑预设脚本。NaumiAgent 不采用某个框架，不构成其能力更强的证据。

第三，产品入口随时间变化。扣子官方说明在 2026-09-08 调整了扣子内新建编程项目的方式，转向在 Agent 中调用相关插件；这不等于扣子编程整个平台停止支持开发。材料必须限定对象和范围，不能拿旧界面截图解释所有现状。[官方变更说明](https://docs.coze.cn/cozespace_5uu7ba6t)

这些页面在 2026-09-11 核对。动态文档不是完整历史快照；本章没有做安装对测，也未测量竞品吞吐、成功率或成本，不作“全面领先”的结论。

## 三道项目定位追问，怎样完整回答

### 为什么不直接基于 LangGraph 开发？

考察的不是你是否忠于自研，而是你是否知道自建的代价。示范回答：如果需求主要是有状态编排和既有生态集成，我会优先评估成熟框架。本项目的学习价值是深入实现和审查目标账本、工具授权、完成证据与恢复契约，因此选择从自己的 Runtime 看这些边界。但框架并不妨碍加入业务安全逻辑，自建也意味着自己承担兼容、持久化迁移与故障维护。

继续追问：迁移框架会保留什么？保留领域契约、评测集、权限和证据语义，而不是机械搬运所有控制流。代价怎么比较？先用一个真实纵向场景验证集成改动量、恢复行为与维护成本，不仅比较代码行数。

### NaumiAgent 到底有什么项目亮点？

示范回答：亮点不是热词覆盖，而是能够沿源码解释“模型说完成”与“证据支持完成”的区别，以及授权、任务账本和恢复如何影响最终结果。例如可以从 [Todo 对账](06-Plan与任务账本.md)讲到[完成门](10-可观测性Harness与评测.md)，再指出当前对账覆盖和失败路径的限制。它是可检查的设计与实现案例，不是已经证实的商业壁垒。

继续追问：这些能力别的平台也能做吗？能，差异是具体契约和实现投入。怎么证明你的实现好？拿固定任务集、错误路径和真实终态比较，不能只展示类名或一张架构图。

### 给企业做知识问答，应选什么？

这是设计推理，不是采购建议。示范回答：先看数据范围、更新频率、引用要求、权限隔离与误答代价。若只是已知资料问答，普通检索增强加明确流程就可能够了；只有需要动态选择资料或调用系统完成动作时，才加入更强 Agent 闭环。平台或代码方案的选择取决于部署和定制边界，而不是“上 Agent”三个字。

继续追问：何时不选 NaumiAgent？当现成平台已经满足约束且自建收益不足时。为何不让 Agent 任意检索全部知识？检索入口也要按身份与资料范围过滤，回答带引用不代表越权读取可以接受。

## 一分钟定位练习

选一个你真正复现过的模块，按“共同问题 → 现成方案 → 本项目选择 → 证据 → 未验证边界”讲一分钟。合格标准是能说明一个别人也能实现的共同点、一个有源码依据的具体选择，以及一个没有数据就不能下的结论。避免使用“别人只能”“我们唯一”“全自动安全”这类不可证实措辞。
