# 01｜目标与交互层：先约定怎样才算完成

[返回目录](README.md) · [阅读方法与术语](17-阅读方法与术语.md)

> 读者目标：能区分用户愿望、验收条件和执行授权；知道什么时候澄清、什么时候继续，以及等待和取消应保存哪些信息。
> 题目为按工程问题设计的模拟题，不冒充任何公司的真实面试记录。

## 从一个具体问题开始

刚接触 Agent 时，最容易把它理解成“能够连续回答问题的聊天模型”。聊天模型的主要任务是生成下一段合理文字：你问“北京天气怎样”，它给你一段回答，回合就结束了。Agent 则必须面对一个更难的问题：用户的请求往往不是一个答案，而是一段要在真实世界完成的工作。例如“整理本周客户投诉并给主管发邮件”，这里包含范围、数据源、收件人、语气、是否允许发送、什么算完成等很多隐含条件。

因此，一个合格的 Goal 至少要包含四件事：目标对象、成功标准、约束条件和当前状态。以“给主管发邮件”为例，目标对象是投诉周报；成功标准不是“模型写出了邮件”，而是草稿按约定保存；若另获发送授权，再核验发送结果；约束可能是不能泄露客户手机号、不能越过今天 18 点；状态则记录正在检索、等待确认、发送失败或已经完成。把这些信息只放在一段自然语言里，下一次对话或进程重启后就很容易丢失。

交互层的另一个职责是管理“不确定性”。不是每件事都应该先追问十个问题：读取当前目录、生成一份草稿这类低风险、可逆动作可以直接做；但删除数据、发送外部消息、花钱、访问敏感资料等动作，只要用户的范围或授权不清楚，就必须停在一个人能理解的确认点。好的确认不是笼统地问“是否继续”，而是展示将做什么、影响哪些资源、能否撤销、用户可以修改什么。

以 NaumiAgent 为例，用户在终端发起 Goal 后，运行态并不只返回一段文本。Todo、后台任务、浏览器任务与子 Agent 会被投影出来；需要人为动作时，系统保留等待状态。面试时可以用这个例子说明：我们不是让模型“猜用户同意了什么”，而是把用户输入、权限确认和终态回执做成不同类型的事件。对初学者而言，这也是设计 Agent 的第一原则：先定义完成与停止，再考虑怎么让模型更聪明。

## 把机制走一遍

教学案例：用户要求“整理本周投诉，生成给主管的周报”。先固定数据时间范围、收件对象和交付形式；系统可先产出本地草稿。用户补充“只生成，不发送”后，发送步骤应被移除，不能因为原计划中有发送就继续执行。完成证据是草稿存在、投诉数量和引用可核对；邮件是否送达是另一项独立验收。发件箱记录也未必代表对方已收到。

## NaumiAgent 源码走读与边界

[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)：源码使用 SQLite 保存 Goal，字段包括 objective、status、note、session_id、pursuit_run_id 和时间。ACTIVE、PAUSED、BLOCKED 是未终结状态；COMPLETED、CANCELLED 是终态，迁移表不允许重新打开。数据库限制一个工作区只有一个未完成目标，create 会把并发冲突转换成用户可理解的错误。这里并没有独立的结构化“验收条件”字段，所以不能宣称 GoalStore 自身已经能验证任意业务成功。

[normalize_interaction_request / normalize_interaction_response](../../src/naumi_agent/user_interaction.py)：交互对象检查选项数量、长度和返回选择是否合法。这保证输入格式，不证明回答者的身份或业务权限；身份确认要在其他边界完成。

对应测试：[test_goal_store.py](../../tests/unit/test_goal_store.py)、[test_user_interaction.py](../../tests/unit/test_user_interaction.py)。阅读函数与断言后再运行；测试文件的存在本身不能证明生产可用。

## 面试陪练：从概念到追问

### 1. 概念题：Goal 与聊天消息有什么区别？

考察意图：能否把需求转成可追踪状态。

回答顺序：结论 → 工作机制 → 本章项目证据 → 适用边界。

示范回答：聊天消息是一条输入，Goal 是跨消息维护的工作方向。例如“报告只保留华东数据”更新任务范围，并不自动成为新任务。Goal 需要状态和终止规则，但业务验收仍需另外定义。NaumiAgent 保存目标及其关联运行，不能仅看 completed 字段就认定报告正确。

继续追问：一条消息涉及两个目标？→先拆分范围再决定是否顺序执行；目标与验收冲突？→以最新有效要求更新验收。

常见失分：把写入 completed 等同于业务完成。

证据入口：[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)；设计类回答是教学方案，不能当成现有产品保证。

### 2. 设计题：什么时候应该追问，而不是立即开始？

考察意图：是否理解不确定性的代价。

回答顺序：结论 → 工作机制 → 本章项目证据 → 适用边界。

示范回答：我先判断缺少的信息是否改变交付、授权或不可逆影响。只缺报告配色，可采用明确默认值先生成草稿；不清楚发给谁，就不能发送。澄清应展示具体选项和影响。对于已经明确授权的低风险步骤，继续执行可以减少用户负担。

继续追问：用户不回答？→保持等待，不把超时当同意；用户补充范围？→更新尚未执行步骤。

常见失分：凡事追问，或者凡事猜测。

证据入口：[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)；设计类回答是教学方案，不能当成现有产品保证。

### 3. 项目题：这个项目如何让目标跨会话保存？

考察意图：能否定位真实持久化代码。

回答顺序：结论 → 工作机制 → 本章项目证据 → 适用边界。

示范回答：我会从 GoalStore.create 进入 SQLite 写入，再看 current 和状态迁移表。测试包含关闭再读取、并发创建和终态限制，因此能讨论存储行为。它目前以工作区管理一个未完成 Goal，适合持续工作方向，并非任意多目标协作系统。

继续追问：为什么只允许一个？→降低活动目标歧义，代价是并行目标需另建模型；Goal 保存了进程吗？→没有，恢复执行要关联运行证据。

常见失分：说所有工作都能自动从任意中断点继续。

证据入口：[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)；设计类回答是教学方案，不能当成现有产品保证。

### 4. 故障题：用户取消时，发送工具已经执行了怎么办？

考察意图：区分取消计算与撤销业务。

回答顺序：结论 → 工作机制 → 本章项目证据 → 适用边界。

示范回答：先停止未来动作，再查询发送结果。如果还没提交，可以取消；如果服务已经接受，应该报告事实并检查是否提供撤回接口；结果未知则进入对账。取消令牌只能影响支持取消的执行路径，无法逆转已经发生的外部副作用。

继续追问：网络超时？→查询业务 ID，别立即重发；撤回失败？→明确交付影响并让用户处理。

常见失分：承诺取消按钮会回滚一切。

证据入口：[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)；设计类回答是教学方案，不能当成现有产品保证。

### 5. 取舍题：怎样证明自治程度提升了，而非只是少弹窗？

考察意图：是否能提出可测量指标。

回答顺序：结论 → 工作机制 → 本章项目证据 → 适用边界。

示范回答：我会同时看任务成功率、无效澄清次数、人工介入比例和越权动作数。减少弹窗只有在成功率和安全约束保持时才有意义。简单任务可走轻流程，含外部发送的任务保留明确确认。数值要来自评测，不能拿主观体验当生产收益。

继续追问：如何控制题目难度？→固定任务集比较；哪些确认可缓存？→仅缓存限定范围且仍有效的授权。

常见失分：只用自动执行次数证明智能。

证据入口：[GoalStatus、_ALLOWED_TRANSITIONS、GoalStore.create](../../src/naumi_agent/orchestrator/goal_store.py)；设计类回答是教学方案，不能当成现有产品保证。

## 动手练习、白板题与验收

用纸或本地 Markdown 写出周报 Goal、两个验收条件和一次澄清。运行本章测试，定位“并发创建”和“终态不可重开”的断言。然后写出用户取消发生在生成前、生成后、发送后时各自的处理。

仓库根目录运行（需已完成项目开发环境安装）：

```bash
.venv/bin/python -m pytest tests/unit/test_goal_store.py -q
```

白板评分：每种取消时机 1 分；区分草稿和送达证据 1 分；说明一个工作区单 Goal 的限制 1 分。达到 4/5 再进入下一章。 本章实验范围与本轮实际执行结果见[验证记录](18-评审与验证记录.md)。
